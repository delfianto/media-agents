# Incident history

Real bugs found while building and smoke-testing this skill against actual files in this library (a real 4K HDR10+Dolby Vision remux, and a real anime episode), in the same spirit as `track-strip/reference/incidents.md` -- the fixes behind several safety/correctness details in `presets.py`, `gpu.py`, and `run.py` came from here, not from reading documentation alone.

## Valid output was deleted because its frame count correctly matched the source

**What happened:** the first full Fallout re-encode after fixing grain synthesis completed all 102,938 frames in 1h42m at 22.45 Mb/s, then verification rejected it as carrying a stale `NUMBER_OF_FRAMES` tag. `mkvpropedit` had recalculated that value from the output, but a correct same-frame-rate transcode naturally has exactly the source's frame count. The normal failed-verification cleanup removed the temporary output, wasting the completed encode.

**Fix:** stale-statistics detection only compares `BPS` and `NUMBER_OF_BYTES`, which must change when HEVC/TrueHD become AV1/Opus. `DURATION` and `NUMBER_OF_FRAMES` are explicitly allowed to equal the source. A regression test presents recalculated output statistics with the same frame count and requires verification to accept them.

## Grain-routed CPU encode preserved the grain and produced 41.8 Mb/s AV1

**What happened:** a 71-minute Fallout UHD Blu-ray remux was correctly identified as noisy and routed from the RTX 4080 to CPU/SVT-AV1, but the 1h46m encode only shrank 30.74 GiB to 21.09 GiB. The real video rate was 41.8 Mb/s. MediaInfo also displayed impossible 57.5 Mb/s/28.8 GiB video and 2.8 Mb/s/1.41 GiB audio figures because ffmpeg had copied the source HEVC/TrueHD `BPS-eng` and `NUMBER_OF_BYTES-eng` tags unchanged.

**Root cause:** the preset set `film-grain=10` but relied on old assumptions about its behavior. SVT-AV1 4.1 defaults `film-grain-denoise` to 0; its startup banner confirmed `film grain synth / denoising / level: 1 / 0 / 10`. Source grain therefore remained expensive coded detail, with synthetic grain signaling layered on top. A blanket HDR quality adjustment also changed the intended 2160p CRF 20 to an unusually conservative CRF 18. Separately, `-map_metadata 0` plus automatic per-stream metadata mapping copied codec-derived source statistics onto transcoded streams.

**Fix:** every grain-enabled SVT preset now explicitly sets `film-grain-denoise=1`; HDR retains 10-bit/color/dynamic metadata but no longer changes the CRF/CQ target; global and transcoded-stream metadata copying is disabled and only language/title are restored. After encoding, `mkvpropedit --add-track-statistics-tags` scans the new tracks and writes their real BPS/duration/frame/byte counters. Verification rejects counters copied verbatim from the source and reports measured before/after sizes and overall rates. Three representative 8-second Fallout samples measured the corrected CRF 20 output at 40% of the broken path's bytes (CRF 22 was 34%, retained only as a comparison). A real short encode produced 17.38 Mb/s overall (70.4% smaller than its remux sample), confirmed SVT's startup banner reports denoising enabled, preserved Dolby Vision Profile 10.1 plus HDR10 fallback, and made MediaInfo report measured 16.9 Mb/s AV1 and 490 kb/s Opus track rates.

## `opus_bitrate_kbps` was non-monotonic for uncommon channel counts

**What happened:** the first implementation used a sparse table for the common layouts (mono/stereo/5.1/7.1) plus a separately-anchored linear formula (`48 + 56 * channels`) for anything else. `test_opus_bitrate_kbps_*` in `test_presets.py` (written before any real file was touched, per this repo's convention of testing "nontrivial parsing/threshold tuning" up front) caught that 5 channels estimated *higher* (328k) than the real 6-channel/5.1 table figure (320k) -- a file with a bare 5.0 track (rare but real) would have gotten a higher bitrate than a 5.1 track with an LFE channel, backwards.

**Fix:** replaced the sparse-table-plus-separate-formula shape with a single piecewise-linear interpolation anchored at the four real data points (1->64k, 2->128k, 6->320k, 8->450k), which is monotonic by construction. Any future anchor point must keep the whole sequence monotonic, or the same test will catch it again.

## The GPU capability probe's synthetic clip was too small for `av1_nvenc`

**What happened:** `gpu.detect_av1_nvenc_gpu()` hands each GPU index a trivial, throwaway `av1_nvenc` encode to check real capability rather than matching GPU names/architectures (see `reference/presets.md` for why that matters on this exact machine). The first version used a 64x64 synthetic test frame. Run for real, it failed on **both** GPUs, including the RTX 4080 that demonstrably encodes AV1 fine at real resolutions:

```
[av1_nvenc] InitializeEncoder failed: invalid param (8): Frame dimensions
are less than the minimum supported value.
```

128x128 hits the same error; 192x192 and 256x256 don't. The probe was conflating "this GPU can't encode AV1" with "this GPU's AV1 encoder has a minimum frame size the test clip didn't meet" -- on a capable GPU it would have reported `None` (no AV1-capable GPU found) and silently fallen back to the much slower CPU path for every run, exactly the failure mode the capability-probing design was meant to avoid.

**Fix:** the probe clip is `256x256`, safely clear of the floor. Confirmed against both real GPUs afterward: GPU 0 (RTX 4080) succeeds, GPU 1 (RTX 3060) still correctly fails with `"No capable devices found"` -- a real capability difference, not a resolution artifact.

## `-b_ref_mode each` is accepted by ffmpeg's CLI parser but rejected by the driver

**What happened:** the NVENC preset defaults initially used `-b_ref_mode each` ("each B-frame as reference" -- the strongest of the three modes ffmpeg documents for this option, `disabled`/`each`/`middle`). It's a real, documented `av1_nvenc` AVOption value with no warning attached. A live end-to-end smoke test against a real anime clip on this machine's RTX 4080 failed immediately:

```
[av1_nvenc] Each B frame as reference is not supported
[av1_nvenc] No capable devices found
```

That second line is misleading on its own -- it reads like a capability problem with the *whole GPU*, not a rejected option value, and would have sent debugging effort toward `gpu.py`'s detection logic instead of `command.py`'s NVENC arguments if the smoke test hadn't been narrowed down argument-by-argument first.

**Fix:** switched to `-b_ref_mode middle`, confirmed directly to open and encode successfully on the same GPU/preset/tune combination. `each` may work on other NVENC generations/driver versions; this wasn't re-tested elsewhere, so treat `middle` as the known-good floor rather than assuming `each` is universally broken.

## Progress-tick throttling didn't recognize not-yet-resolved ticks as ticks

**What happened:** `run.stream_ffmpeg()` throttles ffmpeg's periodic `frame=...` stats lines (at most once per `min_progress_interval`) while forwarding every other line (banners, warnings, errors) immediately, so a multi-hour encode doesn't flood whatever captured its stdout. The first version detected "is this a tick" by checking whether `_PROGRESS_RE` (requiring a resolved `time=HH:MM:SS`) matched. During SVT-AV1's lookahead buffer fill at the start of a real encode, ffmpeg emits the *same* periodic stats line every ~0.5s but with `time=N/A speed=N/A` -- `_PROGRESS_RE` never matches those, so every single one of them bypassed the throttle and printed immediately, for as long as ~10 seconds at the start of a real 4K clip.

**Fix:** tick detection now checks `line.startswith("frame=")` -- independent of whether a time/speed value has resolved yet -- while `_PROGRESS_RE` is still used only for the separate job of *annotating* a line with a computed percentage/ETA when one is derivable. Reconfirmed against the same clip: the `N/A` period now throttles at the same interval as the rest of the encode.

## CRF/CQ-only encoding produced a file *larger* than the source

**What happened:** reported directly by the user against a real file from a different (non-Blu-ray-remux) library: a 3840x2160 x264 source, deliberately bitrate-capped to 15 Mbps (2-pass VBR, `vbv_maxrate=43.2Mbps` -- MediaInfo confirmed this exactly), was already larger than its own source size by 70% through the encode. Every preset here was tuned against Blu-ray *remux* sources (40-80+ Mbps 4K masters, wastefully high for their actual content complexity) where AV1 at CRF/CQ 20-22 undercuts the original easily. CRF/CQ target a *quality level*, not a *size ceiling* -- fed an already-efficiently-encoded source instead, hitting that same quality bar can legitimately need more bits than the source itself used. `verify_output()` already had a "larger than source" check, but only as a post-hoc warning *after* the wasted encode -- there was no ceiling anywhere in the actual encode path.

**Fix:** every encode now caps output video bitrate to a fraction (`presets.MAX_BITRATE_FRACTION_OF_SOURCE`, default 0.85) of the *source's own* video bitrate -- SVT-AV1's "Capped CRF" mode (`--mbr`, alongside `--crf`) and NVENC's `-maxrate`/`-bufsize` (alongside `-cq`). Both mechanisms confirmed directly against real clips before shipping: uncapped NVENC CQ=22 on a real 4K clip produced ~17.9 Mbps, `-maxrate 4M -bufsize 8M` brought it to ~4.4 Mbps; SVT-AV1's own startup log explicitly names the mode (`BRC mode ... capped CRF`) once `mbr` is set. Re-ran end-to-end against a fresh 20s extract of the exact file that exposed the bug (same library, `ffmpeg -c copy` extract, never touching the real file) -- output landed at 90% of source size instead of exceeding it. This is a safety net, not a guarantee of dramatic savings on already-tight sources: on a genuine wasteful Blu-ray remux the cap essentially never binds, since CRF/CQ-driven output lands far under it anyway.

## `-map 0` was quietly including cover-art "video" streams in the AV1 encode

**Side finding while fixing the bitrate cap:** adding per-stream language filtering required switching from a blanket `-map 0` to mapping specific stream indices, which surfaced a latent issue in the old blanket-map approach: a source with an embedded cover-art image (a second, `attached_pic` "video" stream) would have had `-c:v` apply to *both* streams, running the cover art through AV1 encoding alongside the real video. `probe.py` already excludes `attached_pic` streams when picking the *primary* video stream, but the old command-building code mapped every stream anyway. Now only `probed["video"]["index"]` is ever mapped as video -- cover art is dropped entirely (Plex/Jellyfin use `poster.jpg`/`fanart.jpg` files, not embedded cover art, so nothing is lost).

## NVENC preset p6 vs p7: no measured speed difference on this hardware

**What happened:** every preset defaulted to NVENC `-preset p6`, on the unverified assumption (carried over from the general "higher preset number = slower" intuition that holds for most encoders' preset ladders) that `p7` would cost meaningfully more time for little quality gain -- written up that way in `reference/presets.md` without ever actually measuring it.

**Fix:** measured directly on this machine's RTX 4080 -- the same 12s 4K clip, same `cq`/`tune`/AQ settings, encoded 4 times alternating `p6`/`p7`. Results: both took ~10s wall-clock (no measurable difference once past a one-off cold-start outlier on the very first run), and `p7` produced a marginally *smaller* file at the same `cq`. Switched every preset's `nvenc_preset` to `p7` (including the "sd" tier, previously `p5` -- if the most expensive resolution shows no penalty, a cheaper one won't either). This was measured only on this specific GPU/driver combination (Ada Lovelace, driver 610.43.03); if this skill ever runs on meaningfully different NVENC hardware, it'd be worth re-measuring rather than assuming the same holds.

## MKV cover art: `-disposition:v attached_pic` is silently a no-op

**What happened:** the first attempt at embedding cover art followed the pattern used for e.g. audio-file album art -- map the poster image as a second video-type output stream and flag it `-disposition:v:1 attached_pic`. `ffmpeg` accepts this with no warning or error at any verbosity level, and the resulting file plays fine, but the flag never actually takes -- confirmed directly with `mkvmerge --identify` (the authoritative tool for what a Matroska file actually contains): the disposition came back `attached_pic: 0` regardless of exact command form tried (`attached_pic`, `+attached_pic`, targeting `v:0` alone, before or after other output options). ffprobe's own `-show_streams` view doesn't surface anything to contradict this either -- it just shows a second ordinary "video" stream, no hint that anything is missing.

**Why:** `attached_pic` disposition is an MP4-family convention (cover art *is* literally a flagged stream there). Matroska has a completely different, unrelated mechanism: real container-level **attachments** (the same mechanism this skill already uses read-only for font attachments, mapped via `0:t?`) -- not a video stream at all.

**Fix:** ffmpeg's `-attach <path>` output option, confirmed correct via `mkvmerge --identify` showing a genuine `Attachment ID` entry (not an extra `Track ID`). Two more things had to be right before it actually worked: `-attach` requires an explicit `-metadata:s:t:N mimetype=...` or ffmpeg refuses to write the file at all (`"Attachment stream N has no mimetype tag and it cannot be deduced from the codec id"` -- a real error, not a warning); and `N` is *not* always `0` -- it's one past however many attachment-type streams the source already had (e.g. font attachments mapped via `0:t?`), confirmed by deliberately muxing a source with one pre-existing attachment and watching ffmpeg's own error name the *next* index. `probe.py`'s new `attachment_count` field exists specifically to get this right (`command.cover_art_args`).

## `--output-dir` inside `--root` got walked into mid-run and re-encoded its own output

**What happened:** run for real against a genuine library file (`Incoming/Dune.Part.One.2021...Tezcat74.mkv`, 76.2 GB, Dolby Vision + HDR10+) with `--output-dir /mnt/exos1/media/transcode` -- a plain subdirectory created directly under the library root, not under the `.cache/` prefix the default backup/log dirs use. `cli._walk_media_files` builds its file list with `os.walk(root)`, which is a *live* generator: directory contents are read lazily, only when the walk actually descends into them. `transcode/` sorts after `Incoming/` alphabetically, so by the time `os.walk` got there the single-file run had already finished encoding and written `transcode/Incoming/Dune...mkv`. That fresh output matched the same `--path` substring filter as the original source, so the walk picked it up as a second "new" file to convert -- re-encoding an already-AV1-encoded file a second time (real generation loss, not just wasted time) into `transcode/transcode/Incoming/Dune...mkv`. Ended up with two copies on disk: the correct 43 GB output at `transcode/Incoming/...`, and a doubly-compressed, smaller 27 GB decoy one level deeper that should never have existed. `[APPLIED] changed=2` in the run's own summary line was the tell -- a single-file `--path` invocation should never report more than one file changed.

**Why this didn't show up in testing:** the default backup dir (`.cache/transcode/originals`) and log dir (`.cache/transcode/logs`) both live under a dot-prefixed directory, already excluded from the walk by the existing `not d.startswith(".")` filter -- so in-place mode (the only mode exercised by the automated test suite and by earlier smoke tests) never hit this. It's specific to `--output-dir` pointed at a plain, visible subdirectory of `--root`, which the SKILL.md examples show as a normal, encouraged usage pattern (`--output-dir /converted`) -- just never one that happened to sit *inside* the root being walked until this run.

**Fix:** `_walk_media_files` now takes an `exclude_dirs` set of resolved absolute paths and prunes any matching subdirectory from `os.walk`'s traversal exactly like `SKIP_DIR_NAMES` already does by name. `cmd_run` populates it from the resolved `--output-dir`, `--backup-dir`, and `--log-dir` before the walk starts, so any of the three -- default or explicitly overridden -- is excluded regardless of whether it happens to live under `.cache/` or in plain sight. Separately, `--output-dir` output was changed from mirroring the source's path relative to `--root` to a flat `<output-dir>/<filename>.mkv`, which also sidesteps a related annoyance (nested nonsense directories for a single-file conversion) without depending on the exclusion fix alone; a `--overwrite-existing` flag was added since flat output makes a destination-filename collision across different source subdirectories more plausible than the old mirrored layout did. The 27 GB decoy file from this run was deleted by hand after the fact; the 43 GB correct output was kept and verified independently.

## GPU Dolby Vision: ffmpeg av1_nvenc cannot keep RPU; nvencc can

**What happened:** the skill originally forced every Dolby Vision source onto CPU `libsvtav1 -dolbyvision` because ffmpeg's `av1_nvenc` has no RPU-passthrough option -- confirmed on the local ffmpeg build (only `libsvtav1` exposes `-dolbyvision`). Community workarounds that "inject" RPU after encode typically target HEVC (`dovi_tool inject-rpu` is HEVC-only on 2.3.3 here); AV1 needs either SVT's native path or an encoder that attaches DV itself.

**Fix:** when GPU is selected and the source has Dolby Vision (or HDR10+), `run` builds a **nvencc** command (`nvencc_cmd.py`) with `--dolby-vision-rpu copy` and AV1 DV profile `10.1` (and/or `--dhdr10-info copy`). Without `nvencc` on PATH, auto still falls back to CPU for DV so metadata is never silently dropped. Verification now fails the job if a DV (or HDR10+) source produces an output without that metadata. **Still required before library-wide reliance:** a short-clip smoke test on a real remux from this library confirming profile 10.1 lights DV on the actual playback path.

## `--video-metadata copy` (nvencc) doesn't set color signaling -- it copies stale tags instead

**What happened:** caught auditing the real Dune Part One output produced by the fix above (`Transcode/Dune.Part.One.2021...Tezcat74.mkv`, DV profile 7 -> 10, HDR10+), prompted by the user questioning why its measured bitrate looked "obscenely high" for AV1. Two separate things turned up:

1. `ffprobe` reported `TAG:BPS=59767086` and `TAG:NUMBER_OF_BYTES=69678030734` on the output's AV1 stream -- the second number is *larger than the entire 45 GB output file*, an impossible value for a real measurement of that stream. Both numbers matched the *source* HEVC track's own mkvmerge statistics tags exactly. Traced to `nvencc_cmd.py`'s `--video-metadata copy`, which per `nvencc --help` ("copy metadata from input") copies freeform per-stream tags verbatim, statistics included -- nothing to do with the actual AV1 encode. The real bitrate, measured independently two ways (container-level `format.bit_rate` math, and summing raw packet sizes for the video stream directly), was ~38.5 Mbps, not ~60.
2. Worse: the same output's `color_primaries`/`color_transfer`/`color_space` were all `unknown`, even though the source clearly had `bt2020`/`smpte2084`/`bt2020nc`. `--video-metadata copy` does not control this at all -- NVEncC has entirely separate, dedicated flags (`--colorprim`/`--transfer`/`--colormatrix`/`--colorrange`/`--master-display`/`--max-cll`), confirmed via `nvencc --help`, and `nvencc_cmd.py` never set any of them. This is a real playback-correctness risk, not just a cosmetic one: a full Dolby Vision Profile 10.1 player reads the RPU and is unaffected, but anything falling back to base-layer decode (most non-DV-certified players/TVs/software) had no PQ/BT.2020 hint at all. `run.verify_output` already had a comment acknowledging this exact symptom ("nvencc's DV path often leaves container color_transfer / mastering-display tags empty... confirmed on Dune Part One") and worked around it by treating DV RPU presence as sufficient proof of HDR retention -- papering over the symptom instead of fixing the root cause, and never written up here despite that.

**Fix:** `colorinfo.nvencc_hdr_args` builds NVEncC's real color/HDR flags from the same source fields `colorinfo.svtav1_hdr_params` already uses for the CPU path (reusing the CICP_PRIMARIES/CICP_TRANSFER/CICP_MATRIX allowlists as the "known good, vetted" filter, same rationale as those tables). `nvencc_cmd.py` now calls this instead of `--video-metadata copy`, and sets `--video-metadata clear` explicitly (NVEncC's own documented default, made explicit so a future reader doesn't reach for `copy` again for the same "but what about color info" reason). `probe.py` gained a `color_range` field (previously not captured at all). `command.py`'s ffmpeg path also gained an explicit `-color_range` alongside its existing `-color_primaries`/`-color_trc`/`-colorspace` block, for the same completeness. `run.verify_output`'s HDR/mastering-display check no longer skips itself when Dolby Vision is present on the new stream -- now that nvencc sets these fields correctly, that carve-out would only hide a regression of this exact bug rather than protect against one.

**Blast radius:** Dune Part One was the only file that had gone through this skill at the time this was caught (checked `.cache/transcode/originals` and `Transcode/` directly) -- a real bug, but not yet a library-wide one. Re-encoded once this fix landed; see the corresponding CPU-backend re-encode note if present for the redone file's actual numbers.

## `bitplanenoise` was rejected as the grain-detection metric before it ever shipped

**What happened:** the plan for grain-aware backend routing (route heavily grainy/noisy sources to `cpu` for its `--film-grain` synthesis, clean ones to `nvenc` for speed) started with ffmpeg's own `bitplanenoise` filter -- purpose-built noise estimation, no new dependency, cheap (a single lightweight filter pass). Measured directly against three real files in this library before writing any production code (`ffmpeg -vf "bitplanenoise=bitplane=N,metadata=print" -f null -`, parsed via the `lavfi.bitplanenoise.<plane>.<bitplane>` frame metadata keys):

- A.I. Artificial Intelligence (2001, 35mm scan) -- expected grainy.
- Mission Impossible - The Final Reckoning (2025, digital 4K remux) -- expected clean.
- A SPY x FAMILY episode (flat digital anime) -- expected clean/near-zero grain.

At the LSB (`bitplane=1`), all three saturated in an overlapping 0.7-0.99 range with no useful separation -- the anime episode scored *highest* ("noisiest"), because anime BD encodes commonly add synthetic dither to hide gradient banding, and that dither floods the LSB exactly like real grain does. At higher bit planes (4, 8) the metric increasingly tracked edge sharpness/fine detail rather than grain -- the sharp cel-shaded linework in the anime episode scored noisier than the actual grainy 35mm scan at every bitplane tried. The filter measures generic per-pixel bit-level unpredictability, which correlates with grain, dither, *and* legitimate fine detail/sharp edges all at once -- it can't tell any of the three apart.

**Fix:** switched to a denoise-diff approach instead (`medialib/grain.py`): denoise a sample with `hqdn3d` (tuned to suppress high-frequency low-amplitude noise while preserving edges) and measure how much it changed via `ssim`. Measured against the same three files, same sample points: separated them consistently (anime ~0.007-0.012, the 35mm scan ~0.012-0.015, the digital 4K remux ~0.015-0.017, all as `1 - Y-SSIM`), with tight within-file variance across samples. Heavier than `bitplanenoise` (a real decode + denoise + compare pass per sample instead of one lightweight filter), but still ffmpeg-only, no new dependency. See `reference/presets.md`'s "Grain-aware backend routing" section for the full threshold rationale and its provisional-confidence caveat -- three titles informed the shipped default, not a whole-library audit.

## `svt-av1-hdr` shares the encoder name but not upstream's CRF allocation

**What happened:** replacing the system SVT-AV1 package with `juliobbv-p/svt-av1-hdr` did not change ffmpeg's encoder name: both appear as `libsvtav1`. The existing 2160p-film preset therefore continued to request upstream CRF 20. On the same 12-second Fallout UHD scene, upstream CRF 20 produced 31.147 Mb/s while the fork at CRF 20 produced 50.722 Mb/s. The command was syntactically valid and the output looked high-quality; nothing in the old dry-run/report disclosed that a different implementation with a different rate-control scale was active.

**Fix:** `medialib.svt` reads the loader-resolved library version and detects the fork-only `svt_hdr_get_version` ABI symbol without running an encode. Presets now carry independent upstream and fork CRFs; the measured 2160p-film mapping is upstream 20 to fork 27 (31.263 Mb/s on that scene). Probe, analyze, list-presets, env-check, dry-run, and completion labels expose the implementation/version and active CRF. The fork path also pins the audited quality-sensitive controls instead of inheriting mutable defaults. The same seven-point offset used for the other resolution/profile tiers remains provisional and must be recalibrated with multi-title `compare` runs rather than assumed universal.
